# Crowd Runner 무한 모드 및 온라인 랭킹 개발 계획

- 작성일: 2026-11-12
- 대상: [jinw2540/crowd-runner](https://github.com/jinw2540/crowd-runner)
- 검토 기준: `codex/custom-penguin-crab-models` 브랜치의 [전투 효과 적용 커밋](https://github.com/jinw2540/crowd-runner/commit/690c2b0a8a2a6d33e1ab98b936a9193341e214c5)
- 문서 상태: 구현 전 계획안. 아래 수치와 운영 정책은 초기 제안이며, 플레이 테스트 후 규칙 버전으로 확정한다.


## 구현 상태 — 2026-11-12

핵심 게임·서버·UI를 구현했습니다. 아래 본문은 최초 계획을 보존한 것이며, 현재 연결 방법은 [온라인 설정 안내](online-setup.md)를 따릅니다.

- 공통 엔진은 `shared/endless.js`, 서버 검증은 `shared/run-service.mjs`입니다. 위치는 정수 mm, 계산은 60Hz이며 랭킹에는 업그레이드를 적용하지 않습니다.
- 구간당 144m, 현재+앞 3개+뒤 1개 유지, 1,152m마다 화면 좌표를 옮깁니다. 보스는 매 5구간의 120m 지점에 등장합니다(첫 보스 696m, 이후 720m 간격).
- 무한 장애물은 무리 중심이 접촉선을 지날 때 논리 대형의 좌우 폭으로 한 번 피해를 계산합니다. 스테이지의 개별 모델 충돌과 분리했습니다. 장애물 움직임은 정수 틱과 고정 방향표를 사용합니다.
- `POST /runs/start`, `POST /runs/:id/inputs`, `POST /runs/:id/finish`, `GET /runs/:id`, `GET /leaderboard?day=YYYY-MM-DD`를 구현했습니다. 경로 앞에는 `/functions/v1/endless/`가 붙습니다. 닉네임은 Supabase의 본인 프로필 정책을 통해 저장합니다.
- 날짜·버전으로 시드를 계산하므로 별도 `daily_challenges` 테이블은 없습니다. `endless_runs`, `endless_input_batches`, `endless_daily_bests`로 저장합니다.
- 입력 재전송·중복 처리·최고 기록 갱신·서버 시간 검사·일일 순위·내 주변 순위·계정별 전체 최고 기록을 구현했습니다. Google 로그인/탐험 저장은 PR #1과 통합했습니다.
- 30/60/120Hz 재현, 점수·권한·재전송·두 계정 기록을 자동 검사합니다. 30분 분량의 가속 논리 계산과 브라우저 20회 재시작을 검증했습니다. 실제 30분 연속 렌더링, 대표 모바일 기기 성능, 운영 부하 검사는 아직 수행하지 않았습니다.
- 실제 Supabase 프로젝트 연결·Google OAuth·실기기 검증이 남았습니다. 아래 출시 체크리스트는 운영 검증을 마칠 때 갱신합니다.

## 1. 목표

펭귄 무리가 끝없이 이어지는 얼음길을 달리면서 게이트를 선택하고, 장애물을 피하고, 게와 싸워 점수를 얻는 모드를 추가한다. 펭귄이 모두 사라지면 한 판이 끝나며, 검증된 점수로 다른 플레이어와 경쟁한다.

첫 공개에서는 **무한 코스, 거리 중심 점수, 일일 랭킹, 개인 최고 기록, 닉네임**에 집중한다. 현재 스테이지 모드는 별도로 유지한다.

| 모드 | 코스 및 시작 조건 | 기록 |
| --- | --- | --- |
| 기존 스테이지 | 기존 스테이지와 업그레이드 사용 | 기존 별·코인·진행도 유지 |
| 무한 모드 — 랭킹 도전 | 그날의 공통 코스, 동일한 시작 인원 | 서버 검증 후 일일 랭킹 등록 |
| 무한 모드 — 연습 | 같은 엔진과 규칙 사용, 오프라인 가능 | 기기 내 연습 기록으로 표시 |

실시간 동시 대전, 친구 초대, 고스트 재생, 시즌 보상은 첫 공개 범위에서 제외한다.

## 2. 현재 코드에서 바꿔야 하는 부분

| 현재 구조 | 필요한 변경 |
| --- | --- |
| `genLevel()`이 스테이지 전체를 생성 | 무한 모드용 구간 생성기를 별도로 추가 |
| `buildLevel()`이 한 판의 길과 오브젝트를 한꺼번에 생성 | 필요한 구간만 생성하고 지나간 구간은 회수 |
| 보스를 이기면 `finish(true)`로 종료 | 무한 모드에서는 점수를 지급하고 다음 구간으로 진행 |
| `Save`가 진행도를 `localStorage`에 저장 | 로컬 저장을 유지하면서 공용 랭킹 저장소 추가 |
| 시작 인원에 영구 업그레이드 반영 | 랭킹 도전에서는 고정된 시작 인원 사용 |
| 화면 프레임 간격에 따라 게임 계산 실행 | 랭킹용 계산을 고정 시간 간격으로 실행 |
| 터치 이동이 `G.x`를 직접 변경 | 터치·키보드를 동일한 입력 형식으로 변환 |
| 장애물 판정이 `CrowdView` 개체의 위치를 사용 | 충돌용 개체 상태를 화면 표시와 분리 |
| 개체 생성에 `Math.random()` 사용 | 판정에 영향을 주는 난수를 시드 기반으로 분리 |

같은 코스를 제공하는 것만으로 동일한 플레이 조건이 완성되지는 않는다. **입력, 개체 배치, 충돌, 전투 결과까지 재현 가능하게 만드는 것**을 온라인 랭킹의 선행 작업으로 잡는다.

## 3. 무한 모드의 게임 규칙

### 3.1 한 판의 흐름

1. 랭킹 도전 또는 연습을 선택한다.
2. 랭킹 도전이면 서버에서 판 ID, 코스 시드, 규칙 버전을 받는다.
3. 정해진 인원으로 출발한다.
4. 게이트 → 장애물 → 게 무리 → 구간 보스가 섞인 코스를 진행한다.
5. 보스를 이기면 점수를 받고 계속 달린다.
6. 인원이 0명이 되면 종료하고 결과를 표시한다.
7. 랭킹 도전은 서버 검증이 끝난 뒤 순위를 표시한다.

### 3.2 초기 튜닝값

아래는 구현을 시작하기 위한 값이다. 공개 전 테스트로 조정하고, 공개한 규칙은 버전별로 고정한다.

| 항목 | 초기 제안 | 의도 |
| --- | --- | --- |
| 시작 인원 | 10명 | 첫 실수에 바로 끝나는 상황 완화 |
| 시작 속도 | 현재 속도 14 유지 | 기존 조작감 활용 |
| 최대 속도 | 20 | 후반에도 장애물을 읽을 시간 확보 |
| 길 생성 단위 | 144 게임 단위 | 현재 구간 간격 24의 여섯 배 |
| 유지 범위 | 현재 구간 + 앞 3개 + 뒤 1개 | 길이와 메모리 사용량 분리 |
| 보스 간격 | 5개 구간, 약 720 게임 단위 | 성장과 전투의 반복 리듬 형성 |
| 인원 상한 | 9,999명 | 계산과 화면의 과도한 성장 억제 |
| 표시 거리 | 게임 단위 1을 1m로 환산 | 점수와 UI의 기준 통일 |

무제한으로 늘어나는 대상은 **진행 거리와 구간 수**다. 화면에 남는 오브젝트 수와 인원 계산에는 한도를 둔다.

인원 상한은 사용자에게 표시한다. 상한을 넘는 게이트 결과는 최대 인원으로 제한하고, 첫 버전에서는 초과분에 별도 점수를 주지 않는다. 상한에 자주 도달해 선택의 의미가 사라지면, 공개 전에 게이트 성장량과 적의 소모량을 조정한다.

### 3.3 난이도 증가

- 진행 거리에 따라 속도, 적 규모, 장애물 조합의 난도를 높인다.
- 속도가 상한에 도달하면 배치와 선택의 복잡도로 난도를 높인다.
- 같은 날짜·규칙 버전의 같은 구간은 누구에게나 같은 구성으로 제공한다.
- 현재 플레이어 인원에 맞춰 적을 즉석에서 증감시키지 않는다.
- 피할 공간이 없는 장애물 조합과 시야 밖에서 시작되는 공격은 생성하지 않는다.
- 게이트 직후 장애물, 전투 중 장애물 등 조합별 최소 간격을 둔다.
- 초반은 학습, 중반은 선택, 후반은 정확한 조작을 요구하도록 패턴을 나눈다.

## 4. 점수와 순위 규칙

### 4.1 점수 공식

```text
점수 = floor(누적 이동 거리 m) × 10
     + 처치한 구간 보스 수 × 500
     + 장애물 무피해 구간 수 × 200
```

- 거리는 앞으로 실제 진행한 거리만 누적한다.
- 좌우 이동, 일시정지, 전투 대기 시간 자체에는 점수를 주지 않는다.
- 보스 보너스는 각 보스 ID당 한 번만 지급한다.
- 무피해 보너스는 장애물이 있는 구간을 끝까지 통과했고, 해당 구간의 장애물로 잃은 인원이 0명일 때 한 번 지급한다.
- 게와 싸워 잃은 인원은 장애물 무피해 판정에서 제외한다.
- 현재 인원수와 최대 도달 인원은 별도 통계로 표시한다.
- 코인 수익 업그레이드는 랭킹 점수에 영향을 주지 않는다.

예: 1,250m 이동, 보스 1회 처치, 무피해 구간 3개이면 **13,600점**이다.

### 4.2 공정한 경쟁 조건

- 랭킹 도전의 시작 인원, 이동 규칙, 게이트와 적 배치는 동일하게 적용한다.
- 영구 업그레이드와 유료 능력치는 랭킹 도전에 적용하지 않는다.
- 외형·목도리·망토 등 장식은 판정과 점수에 영향을 주지 않는다.
- 화면 주사율이나 그래픽 품질을 바꿔도 같은 입력의 결과가 달라지지 않게 한다.
- 밸런스가 다른 규칙 버전의 점수는 같은 순위표에 섞지 않는다.

### 4.3 랭킹 집계

- 하루의 기준은 한국 시간 00:00~24:00으로 제안한다. 내부 시각은 UTC로 저장한다.
- 서버가 시작 시점에 정한 날짜와 규칙 버전에 기록을 귀속한다.
- 자정을 넘겨 플레이해도 시작일의 코스와 순위표를 유지한다. 이전 날짜 기록은 진행 중이던 판의 종료 후 갱신될 수 있다.
- 사용자별로 하루의 최고 검증 기록 하나만 순위표에 표시한다.
- 정렬은 점수 내림차순 → 거리 내림차순 → 기록 확정 시각 오름차순으로 한다.
- 최종 동률에도 순서가 안정적으로 유지되도록 판 ID를 마지막 정렬 기준으로 둔다.
- 상위 100명, 내 순위, 내 주변 순위, 바로 위 기록까지 필요한 점수를 제공한다.
- 개인 전체 최고 기록도 규칙 버전별로 구분해 표시한다.

## 5. 화면 구성

| 화면 | 표시할 내용 |
| --- | --- |
| 시작 화면 | 기존 스테이지, 무한 모드, 랭킹 진입 버튼 |
| 무한 모드 준비 | 오늘의 코스, 고정 시작 인원, 내 최고 기록, 랭킹 도전·연습 선택 |
| 플레이 HUD | 점수, 거리, 인원, 다음 보스까지 거리 |
| 일시정지 | 이어하기, 그만하기, 랭킹 연결 상태 |
| 결과 | 최종 점수, 거리, 보스·무피해 보너스, 최고 기록 갱신 여부 |
| 기록 검증 상태 | 확인 중, 등록 완료, 재전송 대기, 랭킹 등록 불가 |
| 랭킹 | 오늘의 상위 100명, 내 순위와 주변 기록, 닉네임 |

서버 검증 전에는 확정 순위를 표시하지 않는다. 연결이 끊겨도 결과 화면과 로컬 연습 기록은 남긴다.

## 6. 무한 코스와 성능 설계

### 6.1 구간 생성과 회수

- `runSeed + chunkIndex + rulesVersion`으로 구간 구성을 재현한다.
- 게이트·적·장애물의 난수와 장식·유빙·전투 효과의 난수를 분리한다.
- 경계 양쪽의 생성 규칙을 공유해 길이 끊기거나 유빙이 겹치지 않게 한다.
- 진행 중인 전투나 아직 화면에 남는 효과를 포함한 구간은 먼저 회수하지 않는다.
- 재사용할 메시와 삭제할 구간 전용 자원의 소유권을 명확히 한다.
- 공용 모델·머티리얼·텍스처는 구간 회수 때 해제하지 않는다.
- 누적 거리와 현재 화면의 좌표를 분리하고, 일정 거리마다 화면 좌표의 기준점을 옮긴다.
- 기준점을 옮겨도 장애물의 움직임, 물결, 카메라, 입자 위치가 튀지 않게 한다.

### 6.2 장시간 플레이

- 길·적·유빙뿐 아니라 라벨, 전투 효과, 입력 기록도 계속 쌓이지 않게 한다.
- 검증이 끝난 오래된 입력은 브라우저 메모리에서 회수한다.
- 재생 가능한 원본 기록은 정해진 보관 정책에 따라 서버 저장소로 옮긴다.
- 장시간 플레이 중 메모리 사용량이 일정 범위로 안정되는지 측정한다.

## 7. 같은 입력을 재현하는 게임 계산

### 7.1 게임 계산과 화면 표시 분리

논리 상태에는 인원, 위치, 개체 배치, 장애물 상태, 게이트 선택, 전투 결과, 점수를 둔다. Three.js 모델과 뒤뚱거림·목도리·눈먼지는 이 상태를 받아 화면에 표시한다.

현재 장애물 판정이 화면 개체의 `wx`, `wz`와 연결되어 있으므로, 충돌용 개체 배치와 합체·분리 규칙도 논리 모듈로 옮겨야 한다. 화면 프레임이나 애니메이션 진행 상태가 피해량을 바꾸지 않도록 한다.

### 7.2 계산 규칙

- 논리 계산은 초당 60회의 고정 간격으로 실행한다.
- 화면은 기기의 주사율에 맞춰 두 논리 상태 사이를 보간한다.
- 터치와 키보드를 공통 입력인 목표 좌우 위치로 바꾸고, 논리 모듈에서 같은 이동 속도 제한을 적용한다.
- 입력은 틱 번호와 함께 기록한다. 포인터 이벤트가 게임 위치를 직접 변경하지 않게 한다.
- 인원과 점수는 정수로 관리한다. 좌표와 시간의 정밀도·반올림 규칙도 명시한다.
- 움직이는 장애물의 주기 계산과 충돌 경계 처리를 클라이언트·서버에서 동일하게 사용한다.
- 난수 발생 순서가 로딩 순서나 프레임 수에 의존하지 않게 한다.
- 느린 프레임에서 논리 시간을 조용히 버리지 않는다. 복구할 수 없는 지연은 일시정지 또는 랭킹 제외 상태로 명시한다.
- 기존 스테이지의 조작감과 전투 결과에 대한 회귀 검증을 수행한다.

같은 시드·규칙 버전·입력 기록을 넣었을 때 브라우저와 서버가 같은 결과를 내는 것이 이 단계의 완료 조건이다.

## 8. 온라인 랭킹 구조

### 8.1 제안 구성

- 현재 웹 게임: 화면 표시와 입력 수집.
- Supabase Auth: 사용자 식별과 게스트 시작.
- 서버 함수: 판 생성, 입력 검증, 결과 확정, 랭킹 조회.
- PostgreSQL: 판 상태, 검증된 기록, 일일 최고 기록 저장.

Supabase는 [익명 로그인과 계정 연결](https://supabase.com/docs/guides/auth/auth-anonymous), [서버 함수](https://supabase.com/docs/guides/functions), [데이터 접근 정책](https://supabase.com/docs/guides/database/postgres/row-level-security)을 지원한다. 이 구성을 기반으로 게임 전용 점수 검증을 직접 구현한다.

익명 계정은 브라우저 데이터를 지우거나 다른 기기를 쓰면 접근을 잃을 수 있으므로, 기록을 계속 보관하려는 사용자에게 계정 연결을 제공한다. 닉네임은 표시 이름이며, 사용자 식별 키로 쓰지 않는다.

### 8.2 기록 등록 흐름

```text
랭킹 도전 시작
  → 서버가 사용자·날짜·규칙 버전 확인
  → 판 ID와 코스 시드 발급
  → 고정 간격으로 게임 계산 및 입력 기록
  → 입력 묶음을 순서대로 서버에 전송
  → 서버가 이전 검증 상태에서 게임 계산 재실행
  → 종료 결과 검증
  → 개인 일일 최고 기록 갱신
  → 확정 점수와 순위 표시
```

무한 플레이의 전체 기록을 종료 시점에 한 번에 계산하지 않는다. 일정 길이의 입력 묶음을 순차 검증하고, 서버가 만든 중간 상태를 저장해 다음 묶음을 이어서 검증한다.

### 8.3 API 초안

| API | 역할 | 핵심 조건 |
| --- | --- | --- |
| `POST /runs/start` | 랭킹용 판 생성 | 날짜·시드·버전은 서버가 결정 |
| `POST /runs/{id}/inputs` | 입력 묶음 제출 | 소유자, 순번, 틱 범위, 크기 확인 |
| `POST /runs/{id}/finish` | 결과 확정 요청 | 누락 입력 검증 후 서버 점수 확정 |
| `GET /runs/{id}` | 검증·등록 상태 확인 | 자신의 상세 기록만 조회 |
| `GET /leaderboards/daily` | 날짜별 상위·내 주변 기록 조회 | 날짜와 규칙 버전으로 분리 |
| `PATCH /profile` | 닉네임 변경 | 길이 제한 및 안전한 텍스트 표시 |

동일한 입력 묶음과 종료 요청을 재전송해도 중복 처리하지 않는다. 서버가 받은 점수 값은 비교용으로만 사용하고, 등록 점수는 서버 계산으로 결정한다.

### 8.4 데이터 모델 초안

| 데이터 | 주요 필드 |
| --- | --- |
| `profiles` | 사용자 ID, 닉네임, 생성 시각 |
| `daily_challenges` | 날짜, 시드, 규칙 버전, 시작·종료 시각 |
| `runs` | 판 ID, 사용자 ID, 날짜, 버전, 상태, 마지막 검증 틱·상태, 점수, 시작·완료 시각 |
| `run_input_batches` | 판 ID, 순번, 틱 범위, 입력 데이터 또는 저장 위치, 검증 상태 |
| `daily_bests` | 날짜, 버전, 사용자 ID, 최고 판 ID, 점수, 거리, 확정 시각 |

- `daily_bests`는 날짜·버전·사용자 ID 조합을 유일하게 만든다.
- 개인 최고 기록 갱신은 동시에 여러 판이 끝나도 낮은 기록이 높은 기록을 덮어쓰지 않도록 처리한다.
- 순위표에는 공개 닉네임과 점수만 노출하고, 인증 정보와 상세 입력 기록은 노출하지 않는다.
- 접근 정책으로 클라이언트의 점수 직접 쓰기를 막는다. 관리자용 키는 저장소와 브라우저 코드에 넣지 않는다.

## 9. 연결 끊김과 기록 검증 정책

- 탭이 숨겨지거나 일시정지하면 논리 계산과 점수 증가를 멈춘다.
- 짧은 네트워크 끊김에는 미확인 입력을 보관하고 순서대로 재전송한다.
- 미전송 입력의 길이·용량과 복귀 대기 시간에는 한도를 둔다. 초기 복귀 대기 시간은 10분을 후보로 한다.
- 한도를 넘으면 랭킹 등록 불가 상태를 알리고 연습으로 계속할 수 있게 한다.
- 랭킹 도전은 서버와 연결된 상태에서만 시작한다. 오프라인 시작 기록을 나중에 랭킹용으로 전환하지 않는다.
- 입력 순서 바꾸기, 다른 사용자의 판 제출, 동일 판 중복 등록, 불가능한 이동과 인원 증가를 거부한다.
- 서버 경과 시간보다 과도하게 빠르게 제출되는 진행과 허용 크기를 넘는 요청을 제한한다.
- 검증 실패 원인은 구분해 기록하되, 사용자에게는 재시도 가능 여부와 등록 상태를 짧게 안내한다.

서버 재계산은 점수 숫자 조작과 불가능한 진행을 검출하기 위한 장치다. 가능한 입력을 자동 생성하는 봇까지 완전히 차단하는 기능으로 간주하지 않는다.

## 10. 코드 구성 제안

기존 파일은 필요한 지점에서 수정하고, 게임 규칙과 서버 검증은 공통 모듈로 분리한다. 아래 경로는 구현 시 사용할 후보다.

```text
shared/
  endless-rules.js       # 버전별 규칙, 점수 공식, 난이도
  endless-generator.js   # 시드 기반 구간 생성
  simulation.js          # 화면 없는 이동·충돌·전투 계산
  run-protocol.js        # 입력 묶음과 검증 상태 형식
js/
  endless.js             # 모드 전환과 구간 생성·회수
  leaderboard.js         # 인증·전송·랭킹 API 연동
  leaderboard-ui.js      # 랭킹과 결과 상태 표시
supabase/
  migrations/           # 테이블, 인덱스, 접근 정책
  functions/            # 판 시작, 입력 검증, 종료, 조회
tests/
  endless.test.cjs
  simulation.test.cjs
  leaderboard.test.cjs
```

`core.js`의 저장 구조, `scene.js`의 자원 관리, `game.js`의 진행·점수, `main.js`의 입력 처리를 함께 조정한다. 기존 페이지의 스크립트 로딩 방식에서 공통 모듈을 불러오는 방법도 첫 단계에 확정한다.

## 11. 단계별 실행 계획

| 단계 | 작업 | 산출물 및 완료 기준 |
| --- | --- | --- |
| 1. 규칙 확정 | 모드, 점수, 시작 인원, 상한, 날짜 기준 결정 | `rulesVersion`과 튜닝 설정, 대표 플레이 시나리오 |
| 2. 계산 분리 | 고정 간격, 입력 통합, 충돌·난수 분리 | 같은 기록의 브라우저·서버 결과 일치 |
| 3. 무한 코스 | 구간 생성·회수, 보스 이후 진행, 좌표 이동 | 장시간 달리기에서 길·메모리·판정 안정 |
| 4. 점수와 UI | HUD, 결과, 연습 최고 기록, 난이도 조정 | 점수 설명과 실제 계산 일치, 기존 저장 유지 |
| 5. 서버와 랭킹 | 인증, DB, 입력 검증, 최고 기록·순위 조회 | 서로 다른 기기의 검증 기록 공유 |
| 6. 공개 검증 | 모바일·장시간·네트워크·조작 제출 검사 | 출시 기준 충족 후 제한 공개 |

무한 모드의 재미와 서버에서의 재현 가능성을 확인한 뒤 온라인 랭킹을 공개한다. 단계 3~4에서는 로컬 연습 버전으로 먼저 플레이할 수 있게 한다.

## 12. 검증 및 출시 기준

### 게임 규칙

- [ ] 보스를 처치해도 다음 구간으로 자연스럽게 이어진다.
- [ ] 인원 0명일 때 정확히 한 번 종료된다.
- [ ] 거리·보스·무피해 점수가 중복 지급되지 않는다.
- [ ] 인원 상한과 게이트 표시가 일치한다.
- [ ] 동일한 날짜와 버전에서 코스가 동일하다.
- [ ] 기존 스테이지, 별, 코인, 업그레이드, 저장된 진행도가 유지된다.

### 계산과 성능

- [ ] 동일한 입력을 30·60·120Hz 화면에서 재생해 결과가 일치한다.
- [ ] 브라우저와 서버의 최종 점수뿐 아니라 주요 중간 상태가 일치한다.
- [ ] 좌표 기준점 변경 전후에 판정·물결·카메라·효과가 튀지 않는다.
- [ ] 구간 경계에서 길의 틈과 피할 수 없는 장애물 조합이 없다.
- [ ] 30분 플레이 및 20회 재시작에서 자원 수가 계속 증가하지 않는다.
- [ ] 기준 기기를 정하고 데스크톱 60fps, 모바일 30fps 이상을 목표로 측정한다.
- [ ] 저사양에서 화면 품질을 낮춰도 게임 계산 규칙은 같다.

### 온라인 기록

- [ ] 두 기기에서 같은 날짜의 기록과 순위를 볼 수 있다.
- [ ] 낮은 기록과 중복 제출이 기존 최고 기록을 덮어쓰지 않는다.
- [ ] 점수 직접 변경, 위조 입력, 다른 사용자 판 제출을 거부한다.
- [ ] 일시적 연결 끊김과 재전송 후 기록이 한 번만 반영된다.
- [ ] 자정 경계와 규칙 버전 변경 시 기록이 올바른 순위표에 들어간다.
- [ ] 익명 계정 연결과 접근 정책을 확인한다.
- [ ] 검증 중인 기록이 확정 순위로 잘못 표시되지 않는다.

## 13. 공개 및 운영

1. 별도 개발 브랜치에서 구현하고 현재 플레이 가능한 버전을 보존한다.
2. 로컬 무한 모드로 조작감과 난이도를 먼저 조정한다.
3. 개발용 서버에서 기록 검증과 실패 복구를 검사한다.
4. 제한된 인원에게 랭킹 도전을 공개하고 수치를 확인한다.
5. 규칙 버전을 고정한 뒤 정식으로 공개한다.

운영 중에는 평균 플레이 거리, 첫 보스 도달률, 종료 원인, 프레임 속도, 검증 실패율, 입력 업로드량, 판당 서버 처리 시간을 확인한다. 서버 비용은 실제 이용량으로 추정하며 무료 운영을 전제로 잡지 않는다.

밸런스 업데이트는 새 규칙 버전으로 배포하고 기존 판은 시작한 버전으로 검증한다. 문제가 생기면 랭킹 도전의 신규 시작을 중지하고 기존 스테이지와 연습 모드는 계속 이용할 수 있게 한다.

## 14. 구현 시작 시 준비할 항목

- [ ] 초기 튜닝값과 일일 랭킹 정책을 확정한다.
- [ ] 개발용 Supabase 프로젝트와 배포 위치를 정한다.
- [ ] 게스트 계정의 영구 계정 연결 방법을 정한다.
- [ ] 대표 데스크톱·모바일 테스트 기기를 정한다.
- [ ] 입력 기록 보관 기간, 서버 사용량 한도, 랭킹 장애 시 동작을 정한다.

서버 준비와 별개로 규칙 모듈, 고정 간격 계산, 무한 코스, 로컬 점수 화면부터 구현할 수 있다.
